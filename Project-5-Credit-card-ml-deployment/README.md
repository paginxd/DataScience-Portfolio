## Production-среда: uWSGI + NGINX

**Почему не подходит Flask?**

Flask - это development-сервер, он:
- Однопоточный (обрабатывает один запрос за раз)
- Может упасть при большой нагрузке
- Не оптимизирован для статики

**Решение: uWSGI + NGINX**

- **uWSGI** - запускает несколько копий приложения (воркеров)
  - Обрабатывает множество запросов параллельно
  - Управляет процессами и памятью

- **NGINX** - обратный прокси-сервер (стоит ПЕРЕД uWSGI)
  - Принимает запросы от пользователей
  - Раздаёт статику (картинки, CSS)
  - Балансирует нагрузку между воркерами
  - Защищает от DDoS

Типовая схема:
`Client → NGINX (порт 80) → uWSGI (сокет) → Flask App`


## Архитектура сервиса

### Монолит vs микросервисы

В данном проекте выбран **монолитный подход**.

**Обоснование:**
- Простота разработки и деплоя (один Docker-контейнер)
- Низкая задержка (нет сетевых вызовов между сервисами)
- Достаточно для текущей нагрузки (один ML-сервис)
- Легкость тестирования (один процесс)

**Когда переходить на микросервисы:**
- Разные команды отвечают за разные компоненты
- Разные требования к масштабированию
- Нужна независимая выкатка версий

### Брокеры сообщений (RabbitMQ)

В гипотетическом сценарии масштабирования RabbitMQ может использоваться для:

1. **Асинхронной обработки запросов**
   - Клиент отправляет запрос → попадает в очередь
   - ML-сервис забирает и обрабатывает
   - Клиент получает результат через callback

2. **Batch-предсказаний**
   - Накопление запросов в очереди
   - Пакетная обработка раз в N минут

3. **Логирования**
   - Все предсказания отправляются в очередь логов
   - Отдельный сервис-логгер пишет в Elasticsearch

**Пример архитектуры с брокером:**
```text
Client → RabbitMQ (queue) → ML Service → Prediction
↓
Logging Service → Elasticsearch
```

## Логирование и мониторинг

В текущей реализации логирование запросов отсутствует, используется только стандартный вывод Flask для информации о запуске.

## Бизнес-метрики

Помимо технических метрик (Accuracy, F1-score), для бизнеса важны:

### 1. Ожидаемые финансовые потери (Expected Loss)

Формула расчета:
`EL = Σ (Credit_Limit_i × P(default)_i × LGD)`

```text

где:
- `Credit_Limit_i` - лимит карты клиента i
- `P(default)_i` - вероятность дефолта, предсказанная моделью
- `LGD` (Loss Given Default) = 75% (доля потерь при дефолте)
```

**Применение:** модель считается эффективной, если EL снижается по сравнению с baseline (например, одобрение всех заявок).

### 2. Экономическая эффективность (ROI)
ROI = (Сэкономленные_потери - Затраты_на_модель) / Затраты_на_модель

```text
где:
- `Сэкономленные_потери` = потери без модели - потери с моделью
- `Затраты_на_модель` = разработка + обслуживание + инфраструктура
```

**Применение:** положительный ROI означает, что модель окупается.

## A/B Тестирование

### Постановка эксперимента

**Цель:** сравнить текущую модель v1 (RandomForestClassifier) с новой экспериментальной моделью v2 (например, GradientBoostingClassifier или XGBoost).

**Гипотеза:** модель v2 показывает более высокий F1-score на классе дефолта при том же уровне Precision.

### Разделение трафика
**Сплит:** 50/50 случайным образом

**Метод:** по `user_id` (хеш-функция) — гарантирует, что один клиент всегда попадает в одну группу

**Ключ:** `ab_group` = `control` (v1) или `test` (v2)

```python
def get_ab_group(user_id: str) -> str:
    return "test" if hash(user_id) % 2 == 0 else "control"
```

### Метрики оценки
| Метрика                            | Тип          | Обоснование                                                                                             |
|------------------------------------|--------------|---------------------------------------------------------------------------------------------------------|
| F1-score (класс default=1)         | Основная     | Баланс между Precision и Recall. Банку важно и не пропустить дефолтников (Recall), и не ошибиться в хороших клиентах (Precision) |
| Precision (класс default=1)        | Дополнительная| Цена ложного срабатывания (FP) высока — клиенту могут ошибочно отказать в кредите                       |

**Объяснение выбора метрики:** Recall важен, но слишком высокий Recall за счёт снижения Precision приведёт к отказам хорошим клиентам — это прямые убытки.

### Продолжительность теста
**Минимальный срок:** 14 дней (2 недели)

**Целевой объём:** минимум 1000 предсказаний на группу

**Формула расчёта срока:**

```text
Длительность = (1000 × 2) / (суточный_трафик)
При суточном трафике 200 запросов: 2000 / 200 = 10 дней
```

### Статистический анализ
**Метод:** двухвыборочный z-тест для пропорций (F1-score интерпретируем как долю правильно классифицированных дефолтов)

**Формула z-статистики:**

```text
z = (p_test - p_control) / sqrt(p_pooled × (1 - p_pooled) × (1/n_test + 1/n_control))
```
Доверительный интервал (95%):

```text
(p_test - p_control) ± 1.96 × SE
```

### Критерий успешности
| Исход                              | Решение                                                     |
|------------------------------------|-------------------------------------------------------------|
| p-value < 0.05 И ΔF1 > 0.02        | Роллим v2 — модель статистически значимо лучше              |
| p-value >= 0.05                    | Ничья — оставляем v1, собираем больше данных                |
| p-value < 0.05 И ΔF1 < -0.01       | Останавливаем тест — v2 хуже v1                             |



**Дополнительный бизнес-критерий:** если F1-score не изменился, но Precision вырос на >5% — тоже роллим (меньше ложных отказов клиентам).
